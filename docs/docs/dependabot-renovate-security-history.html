Turn Dependabot and Renovate merges into a dated fix history

Merged Dependabot and Renovate pull requests are one of the sources fixdossier reads. This page describes what is kept, what is dropped, and how to run the action so those merges show up as a dated history rather than as a pile of closed PRs you cannot search later.

What is read

The action uses the GitHub API to list merged pull requests from Dependabot and Renovate in the target repository, up to max_pages pages (100 items per page, default 10). A bot PR is treated as security-related only when it is strict about it: it needs a CVE or GHSA id, a security label, or a security word in the title. Routine version bumps without that signal are omitted. That limit is deliberate: otherwise every lockfile refresh would land in the record.

If the API returns 401, 403 or 404, or hits the rate limit, that source is skipped, a workflow warning is printed, and the gap is listed in the record under “Gaps in this record”. The job still succeeds unless you set fail_on_gaps: 'true'. GITHUB_TOKEN is usually enough for public repository pull requests; it is not enough for Dependabot alerts, which are a different API and are not read.

How a bot PR is mapped to a release

If the merge commit is the commit a release tag points at, the row is labelled tag commit match. Otherwise the date heuristic applies: the first stable GitHub Release on or after the merge date. That is often right when you cut a release shortly after merging security bumps, and often wrong if several lines are released in the same week or if the bump was backported. See backports and maintenance branches.

A workflow that keeps the history

Artifact mode is enough to inspect the files. Commit mode writes them back so each run is a dated commit you can point at later. GitHub deletes workflow artefacts after the retention period, so do not rely on artefacts alone if you care about a long-lived copy.

yaml
name: security-record
on:
  release:
    types: [published]
  schedule:
    - cron: '0 6 * * 1'
  workflow_dispatch:
permissions:
  contents: write
  pull-requests: read
jobs:
  record:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: itulo/fixdossier@v0
        with:
          mode: commit
          fail_on_gaps: 'true'

Pin itulo/fixdossier@v0 or @v0.1.2 as you prefer. Full options are in action.yml and the example workflow.

What this does not replace

  • It does not enable Dependabot or Renovate, and it does not merge their PRs.
  • It does not scan your dependencies. An SBOM or a scanner answers that; see SBOM vs security-fix record.
  • It does not read global advisories for dependencies, only published advisories on this repository, plus the bot PRs and keyword commits above.
  • Silent bumps with no security id or label will not appear. If you want those updates in the record, put a CVE/GHSA id or a security label on the PR.

The surrounding EU texts (support periods under Regulation (EU) 2024/2847, evidence and disclosure under Directive (EU) 2024/2853) are discussed on the SUPPORT.md and PLD checklist pages. A list of merged bot PRs is not a compliance filing.
