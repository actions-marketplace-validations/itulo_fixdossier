How an SBOM differs from a dated security-fix record

An SBOM and a dated security-fix record answer different questions. Teams working toward the EU Cyber Resilience Act often need both. This page states what each file is for, what fixdossier does and does not produce, and how the two can sit side by side. It is about engineering artefacts, not about whether any product meets a legal duty.

What an SBOM records

A Software Bill of Materials lists the components in a product or repository at a point in time: names, versions, and usually a standard identifier such as a Package URL. Common formats are CycloneDX and SPDX. Generators such as Syft, cdxgen or a language toolchain produce one. The point is inventory: what was in the build, so you can match it to known vulnerabilities and say which components you shipped.

fixdossier does not generate an SBOM. It does not read CycloneDX or SPDX files, and it does not inventory dependencies except insofar as a merged Dependabot or Renovate pull request appears in GitHub history.

What a security-fix record records

fixdossier reads a GitHub repository's releases and tags, published repository advisories (GHSA), merged Dependabot and Renovate pull requests, and commit messages that look like security fixes. It writes:

  • SECURITY-RECORD.md and security-record.json (schema: fixdossier/v1): a dated log of those fixes, each mapped to a release when a mapping can be made, with the method used for that row.
  • SUPPORT.md: a support-period table built from your support_period_months, optional eol_date, and GitHub Releases. See Generate SUPPORT.md.

The question it tries to answer is: when did this repository record a security fix, and which GitHub Release appears to have shipped it? That is closer to a change history than to a component inventory. Details of mapping and gaps are on advisory-to-release mapping and what the record covers.

Relevant EU texts (for context, not a completeness claim)

The Cyber Resilience Act is Regulation (EU) 2024/2847. Most of it applies from 11 December 2027 (Art. 71(2)). Article 13(8) is about how a manufacturer determines a support period (at least five years, unless expected use is shorter). Annex II, point 7, is about telling users what technical security support is offered and when the support period ends. SUPPORT.md is a maintainer-written statement of intent from your inputs; it does not choose or check that period, and the default support_period_months of 12 is below the five-year figure in Art. 13(8).

The official CRA text also addresses software bills of materials and vulnerability handling in the essential requirements and technical documentation. This page does not restate those articles. Read the Regulation itself for the exact wording. An SBOM and a fix record can both be useful engineering inputs to that work; neither file, on its own, shows that a product meets those requirements.

The revised Product Liability Directive, Directive (EU) 2024/2853, as corrected, applies to products placed on the market or put into service after 8 December 2026, i.e. from 9 December 2026 (Art. 2(1)). It treats software as a product (Art. 4(1)). Arts. 9 and 10 deal with court-ordered disclosure of relevant evidence and a presumption if it is not produced. A dated fix record is one engineering artefact you might keep; it is not a legal file and it may be incomplete. See the PLD evidence checklist.

Using both in a repository

A typical layout is: generate an SBOM in the same release workflow that builds the artefact, store it next to the release, and run itulo/fixdossier@v0 so the security-fix record and SUPPORT.md are updated from GitHub history. Review both. The SBOM will not tell you which of your own commits fixed a GHSA; the fixdossier record will not list every library in the wheel or image.
