Backports, maintenance branches, and mis-mapped releases

fixdossier can map a security fix to the wrong release when the work landed on a maintenance branch, was backported, or sits in a monorepo with per-package tags. This page explains when that happens and what to check. The mapping rules themselves are on how an advisory is mapped to a release.

How a row gets a release

For each fix-like event, fixdossier tries, in order:

  1. Advisory patched versions. patched_versions on a published repository advisory is matched to release tags (including lists and ranges; from v0.1.2, whitespace, commas and || are split, so 11.5.15 12.3.3 is two versions, not 11.5.1512.3.3).
  2. Tag commit match. If the fix commit, or the merge commit of a bot pull request, is the commit a release tag points at (annotated tags are peeled), the row is labelled tag commit match.
  3. Date heuristic. Otherwise the first stable GitHub Release published on or after the fix date is used, and the row is labelled date heuristic (…).

Only published GitHub Releases are used as release rows. A tag with no Release is not enough. Pre-releases and drafts are skipped in SUPPORT.md and in the “first stable release after this date” step.

Where the date heuristic goes wrong

  • Backports. A fix might land on the main line on Monday and be cherry-picked to 1.2.x on Thursday. The date heuristic, looking at the cherry-pick (or at the advisory date), can attach the row to the next main-line release and miss the maintenance release, or the other way around. Advisory patched_versions that list every patched line are the reliable path; the record will then list matches in matched_releases.
  • Maintenance branches only. A commit that never reaches the default branch is invisible if you only run the action against the default checkout. The GitHub API still sees releases and published advisories; it does not, by itself, walk every maintenance branch for keyword commits.
  • Monorepos and per-package tags. “The first stable release after this date” may be a tag for a different package. The action does not know your package layout.
  • Releases outside GitHub. If you ship on another forge or only attach binaries elsewhere, those versions are not in the table.

These limits are also summarised on what the record covers. They are expected behaviour, not a passing test failure.

What to do in the repository

  1. Publish a GitHub Release for every line you actually ship, including backports, using tags that match the versions you put in advisories.
  2. On each published repository advisory, set patched_versions to every line you fixed, with the same version spelling as the tags.
  3. Prefer putting the CVE or GHSA id in the fix commit on each branch you patch, so a later review can find it even if the heuristic is wrong.
  4. When you read the record, treat every date heuristic row as something to confirm, especially around the same week as a maintenance release. From v0.1.1 the markdown lists every matched release for advisory rows; check that list, not only the first release field.

Why this comes up under the CRA and the PLD

Manufacturers who place products with digital elements on the EU market will, from 11 December 2027, be under Regulation (EU) 2024/2847 (the Cyber Resilience Act) for support periods and vulnerability handling. A support window that names several release lines is only useful if you can later show which line received which fix. The date heuristic cannot do that for you.

Under the revised Product Liability Directive (Directive (EU) 2024/2853), a court can order disclosure of relevant evidence (Art. 9), and defectiveness may be presumed if that evidence is not produced (Art. 10(2)(a)). A record that maps a backport to the wrong tag is not “wrong in a way the tool will flag as an error”; it will look complete and still need a human check. This tool does not decide what you must keep or disclose.
